# dsh-explain-assistant · 解释小助手

> 一个 [DSH（DeepSeek Harness）](https://github.com/deepseek-ai) Web GUI 插件：
> 在主对话右上角放一个「**?**」，点开一个**独立浮窗**，用**白话中文**告诉你主 agent 正在做什么。
>
> 模型半天不吭声、或者吐出一堆你看不懂的东西时，用它**盯进度、看有没有走歪**；
> 不懂技术也能**把握项目进行到哪**；还能让它**给你提下一步建议**。
>
> **它只解释，不动手** —— 不向主 agent 发消息、不改它的上下文、不打断它的任务。

---

## 你什么时候会需要它

下面这几种情况，如果你碰上过任意一种，这个插件就是为你做的。

### 一、模型半天不说话，你不确定它是在干活还是走歪了

主 agent 接了任务会连着跑很久：读文件、执行命令、改代码、再验证。这段时间它可能**一连几分钟没有一句人话**，
也可能憋出一大段你看不懂的输出。你不知道它是**在正常推进**、**卡在某一步**、还是**已经跑偏到别的地方去了**。

> 这正是最难受的时刻：既不敢打断它（怕毁掉它正在做的事），又完全不知道进展。

点开小助手问一句「它现在在干什么」，它会告诉你**当前这一步在做什么、为什么做、实际产出了什么**，
并且明确标出这条结论是**已观察到**（它真的读到了主 agent 的工具调用与输出）还是**仅据汇报**（只有主 agent 自己这么说）。
跑偏、卡住、反复重试同一件事，都能从这些步骤记录里看出来。

### 二、你不太懂技术，但你需要知道这个项目进行到哪了

主 agent 的输出默认是写给会写代码的人看的：一串命令、一屏报错、几个文件名。
如果你是这个项目的**需求方、验收方，或者只是想知道「东西做到什么程度了」**，这些内容对你几乎没有信息量。

小助手会把每一步翻成**白话中文**：不写技术文档的口吻，遇到术语**当场**用一句人话解释
（比如「工具调用（就是让电脑去跑一个具体动作）」）。你不必先学会这套黑话，就能听懂它在干什么、做到哪一步了。

### 三、你想让它给你提建议，而不是只当解说

小助手回答的第四个要素固定是**「哪里可以调整」**：如果想改，从哪里入手、有什么代价。
所以你可以不只是问「它在干嘛」，还可以问：

- 「这一步有必要吗？有没有更省事的做法？」
- 「按现在这个进度，还有哪些事没做？」
- 「我接下来该让它做什么？」

它只读、不动手，所以这些建议**不会自己去改任何东西** —— 决定权始终在你手里。

---

## 为什么不能直接去问主 agent

最自然的反应是直接在输入框里问「你现在在干嘛」。但**那一问会插进它正在进行的对话**：
挤占它的上下文、可能改变它接下来的判断，严重时会让它放下手里的活来回答你。

于是很多人干脆憋着不问，一路看到结束也不知道发生了什么。

这个插件把「提问」搬到旁边去做：

| | 主 agent | 解释小助手 |
| --- | --- | --- |
| 你在哪问 | 主对话输入框 | 右上角「?」弹出的浮窗 |
| 会不会打断 | **会**：插进对话、占上下文 | **不会**：完全独立的一条请求 |
| 谁回答 | 正在干活的那个模型 | **你自己单独挑的**模型 |
| 能干什么 | 执行任务 | **只读**：七个只读工具，没有执行、没有写入 |

一句话：**它在旁边看着主 agent，随时把"它正在干什么"讲成人话，而主 agent 完全不知道你在问。**

## 适合谁、不适合谁

**适合你，如果**：

- 你在跑**长时间任务**，中途想随时知道它进行到哪、有没有跑偏（上面的情况一）；
- 你**不写代码**，但需要把握这个项目的进展（情况二）；
- 你想问「这一步有必要吗」「接下来该做什么」，但不想自己动手改（情况三）；
- 你想问，又**不想打断**主 agent、不想让它发现你在问；
- 你希望解释**有依据可查**，而不是听模型编一个像模像样的答案。

**不适合你，如果**：

- 你想要的是让 AI **替主 agent 干活、接管任务、自动纠错** —— 本插件**只读**，做不到，也不打算做；
- 你想要的是**自动监控**（比如进度停滞就自己弹提醒、自己重试）—— 本插件是**你主动点开才看**，
  不做后台告警、不替你介入；
- 你只是想换个主题或调 UI —— 那是另一个插件（如 `dsh-warm-ui`）的事；
- 你期望它**保证省钱**。小助手是独立请求，虽然与主 agent 对话隔离，
  但**同一账户可能共享费用、额度和资源竞争**，插件不承诺"绝无资源竞争"。

## 特点

下面每一条都能在代码里指到落点，不是宣传语。

### 支撑「盯进度」的

| # | 特点 | 具体表现 | 落点 |
| --- | --- | --- | --- |
| 1 | **看得到每一步的成败** | 读的是主 agent 的**工具调用与执行结果**（不是只看它最后那段总结），所以能回答"哪一步在跑、跑成没有" | `src/host/session-context.ts` `renderMainline`；`src/host/record.ts` `fromToolTrace` |
| 2 | **依据分级，不把"它说的"当"已证实"** | 每条依据标「已观察到」/「仅据汇报」/「无从得知」——主 agent 自称"完成了"但没验证，会落在第二级 | `src/host/prompts.ts` `EVIDENCE_TIERS` |
| 3 | **信息不足就明说，不编造** | 拿不到信息时固定写出「该步未提供足够信息」，并说明缺什么，不用空话凑数 | `src/host/prompts.ts` `INSUFFICIENT_MARKER` |
| 4 | **记录没完成会写明原因** | 不是笼统的"未完成"，而是分别给出超时 / 模型失败 / 触及上限 / 没拿到摘要 / 你主动停止，并给补救建议 | `src/shared/record-reason.ts` `RECORD_REASON_TEXT` |

### 支撑「讲成人话」的

| # | 特点 | 具体表现 | 落点 |
| --- | --- | --- | --- |
| 5 | **白话中文，术语当场解释** | 内置 15 条术语对照（工具调用 / 命令 / 终端 / 编译 / 上下文 …），出现时当场用一句话说明，不用行话解释行话 | `src/host/prompts.ts` `TERM_HINTS` |
| 6 | **一次解释覆盖四要素** | 在干什么 / 为什么做 / 实际产出 / **哪里可以调整**，缺一不可 | `src/host/prompts.ts` `FOUR_ELEMENTS` |
| 7 | **模型不可用时仍能看** | 已有问答、你选中的依据、以及一份**本地生成**的基本说明照常显示，并明确标注"这不是模型给出的解释" | `src/client/overlay.tsx` `offlineFallbackNodes` |

### 支撑「不打扰、可信、可追问」的

| # | 特点 | 具体表现 | 落点 |
| --- | --- | --- | --- |
| 8 | **只解释，绝不动手** | 工具白名单只有 7 个**只读**工具；没有执行命令、写文件、联网、操作端口的工具 | `src/host/tools.ts` `TOOL_NAMES` |
| 9 | **不打扰主 agent** | 不写主对话、不把小助手问答注入主 agent 上下文、不取消主任务、不覆盖输入框草稿 | `docs/business-logic.md` §2；宿主侧无任何主对话写入路径 |
| 10 | **可核查的追问** | 追问会带上本会话既往问答，所以「那它为什么要这么做」能接上上一轮 | `src/host/prompts.ts` `buildMessages`（由 `src/index.ts` 注入） |
| 11 | **模型单独选，不跟随主 agent** | 从 DSH 已配置模型里自己挑；**没选就不发请求**，绝不偷偷用默认模型。选择入口在标题栏（显示当前模型名），点开是一整页：按提供方分组、可搜关键词、失败原因写在页内 | `src/index.ts` `resolveModel`；界面 `src/client/overlay.tsx` `buildModelPanel` |

| 13 | **只读工作区，越界直接拒绝** | 路径逃逸（绝对路径、`..`、符号链接出界）一律拒绝并给中文原因 | `src/host/evidence.ts` `resolveWorkspacePath` |

### 界面里你会看到什么

- 右上角一颗 **「?」**（有新内容时是「? ·」）。
- 点开是一个浮窗，标题「解释小助手」，第一次打开会给你 4 个快捷问题：
  「它现在在干什么」「这一步为什么这么做」「这步实际产出了什么」「哪里可以调整」。
- 点浮窗里的「选择主对话内容」，再去点主对话里的**任意一条步骤卡片或一段助手汇报**，
  就能针对那一条提问；浮窗里会常驻显示「正在围绕这条内容提问」。
- 浮窗底部有 `/compact` 按钮、右下角有占用圆环、顶部有历史记录（可展开单条完整内容）。

## 安装

一条命令，装进你的 Web profile（把 `web` 换成你实际在用的 profile 名）：

```bash
dsh plugin add --profile web 'git+https://github.com/yunliya-cuter/dsh-explain-assistant.git'
```

装完**不用手改任何配置**：本包自带 `cordis.patch.yml`，并通过 `package.json` 的
`dsh.bundle.patch` 指向它，DSH 会在安装后自动把包名写进 profile 的
`dsh.profile.bundles` 并在进程内重新装配。

然后**刷新浏览器（F5）**。

### 验证装好了

1. 打开任意一个主对话，右上角工具行里应出现一颗 **「?」**。
2. 点它，浮窗出现，标题是「解释小助手」。
3. 点标题栏里的**模型按钮**（写着当前模型名，没选过则写着「选择模型」）选一个（**不选就不发请求**），然后点一个快捷问题。
4. 几秒内应看到白话中文回答；右下角圆环显示占用百分比或「占用未知」。

### 从本地工作区开发（改代码即时生效）

不想走 git 安装、就在本仓库上改代码时，直接把**本地路径**作为 spec 装进来：

```bash
dsh plugin add --profile web "$(pwd)"
```

改完源码后重新构建、刷新浏览器：

```bash
npm run build                        # tsc 产出 lib/*.js + esbuild 打包 lib/client.js
node --test tests/*.test.mjs         # 跑测试（本仓库没有 npm test 脚本）
```

> `node --test tests/` 这种带目录的写法会失败，**必须带通配** `tests/*.test.mjs`。

### 卸载

```bash
dsh plugin remove --profile web dsh-explain-assistant
```

插件卸载时会自行移除路由、订阅、监听器、计时器和客户端入口。

## 它把数据存在哪

- 位置：`$DSH_HOME/explain-assistant/sessions/<主对话 id>.json`，一个主对话一份文件；
  图片快照在 `$DSH_HOME/explain-assistant/sessions/<主对话 id>/images/`。
- 写入方式：每个主对话一条**独立串行写队列**，写临时文件、校验后**原子替换**正式文件。
- 它**只写自己的目录**：不碰工作区文件，不碰 DSH 共享附件，不碰主对话记录。
- 主对话被归档时，对应的小助手记录与图片快照会被清理（**判据极其保守：拿不准就绝不删**）。

## 性能：拉伸 / 选中 / 打字（2026-11-07）

用户报「拉伸、选中文字、输入文字时卡顿」。三条分别测、分别归因 —— 它们根本不是同一个原因。

测法：无头 Chrome（真机 GPU：AMD Radeon 集显，1418×746，DPR 1.5）连 3082 实例，
页面里挂 rAF 采样器 + `PerformanceObserver(longtask)`，同一段脚本驱动三种交互：

* **拉伸**：按住右下角，每帧一次 pointermove，共 30 帧（每帧 +2.5px 宽 / +1.2px 高）；
* **选中**：把正文一段文字逐帧扩选（30 步），先把这段滚进视野、并让输入框失焦（真机上点正文就会失焦）；
* **打字**：每帧插入一个字符（≈60 字/秒的压测；另测了 10 字/秒的真实速度）。

同时用 CDP 的 `Performance.getMetrics` 取 `LayoutDuration / RecalcStyleDuration / LayoutCount`。
每组跑 3 次取中位数；每跑一组前把窗口拖回 460×560。

| 场景 | 指标 | 修前 | 修后 |
|---|---|---|---|
| 拉伸 | 帧间隔 p50 / p95 / 最大 | 50.1 / 83.4 / 200 ms | **16.7 / 33.5 / 66.6 ms** |
| 拉伸 | 长任务（>50ms） | 14 个 | **0** |
| 拉伸 | 布局耗时 / 次数 | 653 ms / 124 次 | **275 ms / 31 次** |
| 选中 | 帧间隔 p50 / p95 / 最大 | 50.1 / 83.3 / 100 ms | **16.7 / 16.9 / 50.2 ms** |
| 选中 | 长任务 | 28 个 | **0** |
| 选中 | 样式重算 / 布局 | 1348 ms / 225 ms | **44 ms / 0 ms** |
| 打字 | 帧间隔 p50 / p95 | 33.3 / 33.7 ms | **16.7 / 17.0 ms** |
| 打字 | 每个字符的主线程耗时（p50） | 8.9 ms | **0.3 ms** |
| 打字 | 布局次数（30 字） | 180 次 | **60 次** |

### 三个根因

**1. 打字：一个字触发 3 次「整页强制布局」。**
输入框的光标/选区是自绘的（隐形镜面 + `Range.getClientRects`）。旧写法的 `refresh()` 里依次做了
`autosize()`（写 `height:auto` → 读 `scrollHeight`）、`syncMirror()`（`getComputedStyle` + 读 `clientWidth`）、
光标矩形、选区矩形、根元素矩形 —— **每一步都是一次强制布局**；而 `input` / `selectionchange` / `keyup`
三个事件每个字各触发一次 `refresh`。剖面里 `autosize` 690ms + `syncMirror` 435ms，占打字总耗时 59%。
改法：三个事件合并到一帧一次；镜面文字只写一次、随后**一次**把所有几何读完（写→读分离）；
排版属性（字体/内边距/宽度）只在尺寸或主题变化时才重写；支持 `field-sizing: content` 的浏览器
干脆不再由 JS 量高度；光标与选区块的位置从 `left/top`（布局属性）改成 `transform`（合成属性）；
草稿走 `updateDraft` 快通道（草稿不进渲染树，敲字时不再重画整棵浮窗）。

**2. 选中：一条 CSS 规则让整篇文档每次选区变化都重算样式。**
剖面里一次拖选的 `RecalcStyleDuration` 是 1348ms / 60 次重算 ≈ 每次 22ms —— 而脚本只占 37ms。
二分下来是 `dsh-warm-ui` 的 `html[data-wta-motion-sel] ::selection{background:transparent}`：
那个属性**常年挂在 `<html>` 上**，于是文档里任何一次选区变化（包括小助手浮窗里的、根本不归它画的选区）
都要给每个元素重算一次 `::selection` 样式。实测把属性挪到浮窗自己的滚动容器上：
样式重算 1546ms → 1ms、帧间隔 66.6 → 16.7ms。
改法（在 warm-ui 侧）：规则改成 `[data-wta-motion-sel] ::selection`，属性由 `syncNativeSel` 挂到
**当前真正要画的那块滚动容器**上；指针落在别的插件（`.dsh-explain-assistant-overlay` / `.ea-field`）里时
一个属性都不挂。小助手这一侧另加两道：量取时沿祖先链的贵读（裁剪区、底色遮挡、层原点）全部缓存；
在输入框里打字时正文高亮引擎直接不醒（`selectionchange` 在输入框里也会派发，但那跟正文选区无关）。

**3. 拉伸：每一帧都在重新栅格化 28px 的毛玻璃和一圈 80px 的投影。**
只改宽度、不动任何 JS 时，中位帧间隔就已经是 32.9ms；拆开看：关掉 `backdrop-filter` 26.5ms、
关掉投影 19.8ms、两者都关 16.7ms。也就是说拖动时真正贵的是**绘制**，不是 JS。
雪上加霜的是输入框的 `ResizeObserver` 每帧都触发一次完整刷新（又一次 `autosize`+`syncMirror`），
正文区高度的 `ResizeObserver` 每帧读一次 `clientHeight` 再写一次 `--ea-body-h`。
改法：拖动期间给绘制让路（`[data-resizing=true]` 关掉毛玻璃、换成实底 + 小投影），
输入框与正文区的测量都改成「尺寸稳定后再补一次」；松手立刻恢复玻璃。

### 补记：选中之后「看不见框」的两个真 bug（2026-11-07）

用户反馈「选中后看不见橙框」。拆开验了三层（自绘层挂上没有 / 原生选中色是否被抑制 / 有没有东西盖在
高亮之上），最后抓到两个独立的原因，都是这一轮性能改动**引入/放大**的：

**① 框画到了别处（原点缓存没跟着挂载点走）—— 回归。**
高亮层会挂进「真正在滚的那个容器」里，位置按「文字矩形 − 层原点」算。这轮为了省每帧一次
`getBoundingClientRect`，把原点缓存了起来，但**换挂载点时没作废**。
真机复现：刚打开浮窗、还没滚过的时候拖选第一段文字 —— 文字在 y=78，框画在 y=153（正好差一个
`.ea-turn-a` 的原点 76px）；差得再多一点整块就跑到可视区外，看起来就是「选中了，但什么都没有」。
旧构建同场景是 y=106（正确），所以这是本轮引入的回归。修法：`ensureHost()` 换容器时把原点缓存清掉。

**② 深色玻璃上原来的蓝色几乎看不见 —— 老问题，这轮才发现。**
框的颜色是 `rgba(47,107,255,.28)`（蓝）。在深色浮窗（底色约 #4c4f56）上按像素中位数实测：
框内 (69,87,132)、框外 (78,80,84)，对比度只有 **1.13:1** —— 等于没画。
修法：高亮色改成跟随暖色主题的「业务主色」`--dsw-alias-state-business-primary`（就是 warm-ui 在正文里
画的那个橙 #e59f52）34%，拿不到该 token 时退回原来的蓝：

```css
--ea-selection:rgba(47,107,255,.28);                                   /* 兜底 */
--ea-selection:color-mix(in srgb, var(--dsw-alias-state-business-primary,#2f6bff) 34%, transparent);
```

同一位置重测：框内 (126,103,80) vs 框外 (78,80,84)，对比度 **1.52:1**（对下一行 1.77:1），
且与正文里的橙框同色 —— 同一个「选中」动作在浮窗内外不再两种颜色。

**验证口径**（不再用「像素有变化」这种弱指标）：用真鼠标（CDP `Input.dispatchMouseEvent` 按下-拖-松开）
在四个场景各拖一次，量「可见高亮块与选中文字首行的重叠覆盖率」，要求 > 0.6 且框内对比度 ≥ 1.5：

| 场景 | 选中文字 y | 框 y | 偏移 | 覆盖率 |
|---|---|---|---|---|
| 刚打开浮窗就选 | 108 | 106 | −2px | 1.00 |
| 滚动之后再选 | 108 | 107 | −1px | 1.00 |
| 连选第二次 | 108 | 107 | −1px | 1.00 |
| 拖动浮窗之后再选 | 138 | 137 | −1px | 1.00 |

（−2px 是刻意留的 1.5px 内边距，不是误差。）

顺带补了一条：浮窗自己拖边改大小时也会重算高亮（`ResizeObserver` 观察根节点，拖动过程中先不量、
尺寸稳定后再补一次）—— 以前拖完窗口，选区还停在旧折行上。

### 还没有解决的（如实写）

* **拉伸过程中中位帧间隔仍在 16.7~33ms 之间**：面板要按新宽度重新折行十几屏中文，这部分是浏览器的
  文本排版本身（实测布局 275ms/30 帧）。再往下压只有 `content-visibility:auto` 一条路，但它会把
  `scrollHeight` 变成估算值，影响「打开就滚到最新」「流式跟随」这些已经调好的行为 —— 没做。
* **主对话里拖选仍然慢**（实测 p50 100ms+）：那一段是 warm-ui 自己的高亮引擎在画，属性挂在
  `<body>` 上仍是全文档范围。本轮只把小助手浮窗这一段摘干净了。
* 数据来自单机单浏览器（Chrome / Windows / AMD 集显），不代表低端机与 4K 屏。

## 焦点：点开就能直接输入 + 「焦点态」只认真正的焦点（2026-11-07）

用户原话：「我希望点开小助手后默认焦点在输入框来直接输入。另外输入框似乎有一些bug，
会出现焦点不在输入框无法输入却光标仍在闪动或者有光圈等不符合直觉的问题。」

两个都是真的，而且是**两个独立缺陷**，不是同一个问题的两种说法。

### 一、光标在闪，但一个字也打不进去（假光标）

真机复现（点「?」打开浮窗，什么都不点，直接看光标）：焦点停在「?」按钮
（`BUTTON.ea-hbtn-btn`）上，输入框里那根自绘光标却在闪 —— 抬手一打，字全进了主对话。

量化（每帧采样，5 秒，判据是「没有焦点 && 光标在闪」）：

| | 违规帧数 | 打开后头 1.5 秒 |
|---|---|---|
| 旧构建 | **360** | 111 |
| 新构建 | **0** | 0 |

两个根因叠在一起：

1. `refresh()` 结尾**无条件** `restartBlink()`。挂载时那一次刷新就已经画了一根光标；
   之后**任何**一次刷新（窗口改大小、拖浮窗、切主题、字体晚到、滚页面…）都会把失焦后的光标重新点亮。
2. `onBlur()` 只把透明度弹簧推回 0，`caretVisible` 仍是 `true` —— 下一次刷新就认为
   「光标本来就该在」，于是重新点亮并恢复闪烁。

修法：加一个**唯一判据** `focused()`（`document.activeElement === input` 且焦点事件记录为真），
`refresh` / `paintCaret` / `paintSelection` 三处都过它；`onBlur` 把 `caretVisible` 一起置假；
窗口整个失焦（切到别的应用）时也把光标收掉。

### 二、那一圈「光圈」

焦点环原来写在 `.ea-field:has(.ea-input:focus-visible)` 上，两个问题：

* **文本输入框在 Chrome 里连「鼠标点一下」都算 `:focus-visible`** —— 点进输入框就常驻一圈
  2px 内环；深色玻璃上那是接近白色的一圈光（实测 `rgb(223,225,230)`），用户说的「光圈」就是它；
* `:has()` 的失效重算在部分内核版本会漏掉焦点变化 —— 「焦点早走了、环还留着」，正是
  「没有焦点却有光圈」那种不符合直觉的观感。

改成**属性驱动**：`data-focus="keyboard" | "on"`，由 text-field.ts 在真的 focus / blur 时写。
只有**键盘**进来的焦点才给环（鼠标点进来不给），所以「有环」⇔「有键盘焦点」，
两者不可能再错开。对比度不变（品牌色 2px，浅色 4.4:1 / 深色 3.4:1）。

### 三、打开即聚焦：一条明确路径

`deliverFocus(ctx)`：等浮窗挂进文档 + 从加载页切到就绪档 → 投递一次 → **下一帧校验**
`document.activeElement` → 不是它就再补一次 → 仍失败留一条 `console.warn`（不静默）。
不写成「挂载时调一次 `focus()` 就算完」：`focus()` 是下一帧才真正生效的，
期间的焦点可能被宿主或其它模块覆盖 —— 那正是「看起来打开了但打不了字」。

分两种来源，避免「为了能直接输入，就把主对话的焦点抢走」：

* 用户点/按开的（`openedByUser === true`）→ 送焦点，且**每个会话只送一次**（关窗清零）；
* 后台切会话把浮窗带过来（`openedByUser === false`）→ 不碰焦点；若重建前正在这里打字，
  重建后把焦点还给新的输入框。

顺带两条：

* 点「发送 / 停止」之后把焦点交回输入框。鼠标点按钮会让焦点停在按钮上，接着打字一个字都进不去 ——
  和上面是同一类「看着能打字其实不能」。
* **聚焦不再吃掉主对话里的选区**：Chrome 的既定行为是「焦点进文本控件 → 文档选区整体作废」，
  而用户的典型动作恰恰是「在主对话里拖选一段 → 点 ? 问小助手」。实测旧构建点开后选区还在
  （因为焦点根本没动），新构建如果不管就会把那段橙色高亮凭空抹掉。所以 deliverFocus 在
  聚焦前后各留一手，把选区原样还回去（实测：拖选 10 个字 → 点开浮窗后仍是那 10 个字，且焦点在输入框里）。

### 验证（真鼠标 / 真键盘，CDP 驱动真机）

| 场景 | 焦点 | 自绘光标 | 焦点环 |
|---|---|---|---|
| 鼠标点「?」打开 | 输入框 ✅ | 闪（正确） | 无 |
| 打开后**不点**，直接打字 | 输入框 | 闪 | 无（文字真的进了小助手输入框） |
| 点正文（失焦） | 浮窗本身 | 不闪 | 无 |
| 失焦后改窗口大小 / 切主题 / 滚页面 | 不变 | 不闪 | 无 |
| 鼠标点回输入框 | 输入框 | 闪 | 无（鼠标焦点不给环） |
| Tab 出去、Shift+Tab 回来 | 输入框 | 闪 | **有**（键盘焦点） |
| 点「发送」 | 回到输入框 | 闪 | 无 |
| Esc 关闭 | 回到「?」按钮 | — | — |

### 还没解决的（如实写）

* **中文输入法组字没有本轮复测**：没有自动化手段喂真实的 IME 事件；本轮改动只涉及
  「焦点态画不画」，不碰组字链路（composition 事件与 value 都不动）。
* **主对话输入框自己的焦点环不归这个插件管**（那是宿主的 `:focus-visible` 规则）。
* 焦点行为在 Chrome / Windows 实测；Firefox / Safari 只有单元测试层面的保证。

## 上下文压缩提示词：七段底稿 + 可验收判据（2026-11-07）

用户原话：「现在的提示词过于简单且缺少约束性。上下文压缩可以参考 dsh 的提示词针对我们的需求进行优化。」

### 旧提示词到底出了什么问题（有真实摘要为证）

旧实现只有 6 行 `COMPACT_INSTRUCTION`，而且**复用「回答用户」的系统提示词**。翻磁盘上
13 份真实摘要，能稳定复现四个毛病：

| 现象 | 真实例子 | 后果 |
|---|---|---|
| 把系统提示词又抄一遍 | 一份 827 字摘要里有 658 字（80%）是「我是谁 / 四要素 / 说话规则 / 术语表」 | 真正的对话事实被挤掉 |
| 把压缩指令当成用户的话 | 摘要里写「当前这次要求是：把上下文压缩成简短中文摘要」 | 下一轮把指令当用户意图 |
| 把提问脚手架写进摘要 | 「用户没有输入具体问题…本次没有拿到任何步骤依据」 | 摘要里一半是噪音 |
| 只压最近 6 轮 | 10 轮会话只看到后 6 轮 | 前 4 轮的构建、测试、提交号全丢，摘要却看起来完整 |

### 新提示词做了什么

- **独立系统提示词**：压缩器不再带着「解释小助手」的身份读历史，也不会复述回答规则。
- **唯一判据**：一个没读过原文的助手，只看底稿必须能答出五件事（用户/约束/结论+依据/未完成/锚点）；
  任一项答不出就算压缩失败。
- **七段骨架**：用户与当前意图、硬约束与偏好（含否定式）、问过的问题与结论、已更正/已否决/已取代、
  未完成与待跟进、关键锚点（逐字照抄）、已解释术语（术语 + 一句极简定义，最多 10 条）。标题逐字照抄，空段写「无」，不许省段。
- **来源分级**：〔已观察到〕/〔仅据汇报〕/〔无从得知〕必须跟着结论走，不许把「仅据汇报」升级成事实。
- **逐字保留 + 必须丢弃**：原话、否定句、路径、命令、数字、报错逐字保留；寒暄、时间戳采样行、
  被取代的旧方案、工具原始输出丢掉。
- **冲突消解**：同一条事实以最后一次为准，并留下「已取代：旧说法」的痕迹。
- **长度预算**：正文 ≤ 2000 字且 ≤ 原文 60%（原文不足 800 字按 800 字算），超限按固定顺序裁剪。
- **再压缩稳定**：旧底稿当背景合并，不许原样照抄，也不许丢掉仍成立的锚点。
- **不调用工具 / 空输入也有七段**：压缩请求 `tools: []`；空会话输出七段「无」，不拒绝、不追问。
- **宿主侧硬校验**：模型没按七段输出（例如只回一句「我做不到」）→ 判 `INVALID_SUMMARY`，
  不写 `compactState`，上一份可用摘要原样保留。

### 实测 A/B（3082、同一份 10 轮会话、同一模型）

| 指标 | 旧提示词 | 新提示词 |
|---|---|---|
| 必留锚点召回（19 个：TS2307 / 840÷840 / bc5dc0c / md5 / 16.7ms / 端口纠正 / 用户偏好…） | **10 / 19（53%）** | **19 / 19（100%）** |
| 七段骨架 | 0 / 7 | 7 / 7 |
| 脚手架污染（「用户没有输入具体问题」等） | 1 处 | 0 |
| 摘要正文 | 1112 字（输入 1454 字，只看到 6 轮） | 1963 字（输入 2963 字，10 轮全看到；≤2000 硬上限） |
| 空会话 | 454 字拒绝（且被当成摘要存下） | 109 字，七段全是「无」 |
| 再压缩一次 | 未测（旧实现会丢掉更早内容） | 19 / 19 锚点仍在，七段完整 |

一句话：旧版是「看起来像摘要」，新版是「换个人接着干也不用重问」。

### 没做的 / 需要知道的

- **对话提示词**：下一节处理；两边的「已解释术语」标签已经对齐。
- **老摘要不迁移**：磁盘上已有的旧摘要原样保留，下一次 `/compact` 才会按新格式重写。
- **模型差异**：`deepseek-official/deepseek-flash` 与 `workbuddy/cn:deepseek-v4.1-flash` 都实测过；
  期间遇到两次提供方 500/TRANSPORT，是上游抖动，不是提示词问题。
- **这是宿主侧改动，必须重启 dsh web 才生效**，F5 不够。3082 已重启并完成上面的验证；
  3081 只放了构建产物，没有重启（按约定不擅自动 3081）。

## 对话提示词：按问题类型分派 + 输出契约 + 术语台账（2026-11-07）

用户原话：「包括对话的提示词…现在的提示词过于简单且缺少约束性」。讨论后确定：
四要素只用于解释具体步骤、默认长度 ≤250 字、含糊问题先追问、术语改成通用规则 + 示例、
压缩摘要按「已解释术语」台账读。

### 旧提示词的问题（真实回答为证）

从 3082 的真实会话量了 10 条回答：中位数 **1,507 字**、最长 **1,909 字**，6/10 超过 1,000 字。
四个结构性问题：

- 四要素被写成对所有问题「缺一不可」——用户问「3+3」时模型只能违反；
- 没有长度预算，回答越来越长；
- 没有「含糊先追问」「重复提问别复读」的规则；
- 摘要块怎么读、已解释术语怎么用，完全没有写。

### 新提示词的结构

1. **优先级**：不编造 / 不越权 / 不泄露 > 用户本条指令 > 依据分级 > 默认风格。
2. **四块材料**：当前问题 / 选中依据 / 主 agent 上下文 / 记忆（含摘要）。
3. **问题类型决策树**：解释步骤→四要素；问状态→结论/依据/下一步；问事实→直接答；
   含糊→先问一句；多问题→编号；超范围→说明 + 替代。
4. **依据分级**：〔已观察到〕/〔仅据汇报〕/〔无从得知〕；纯算术/常识不标，禁止自造「无需观察」。
5. **不确定与时间**：只引用记录里出现过的时间；没有实时时钟。
6. **摘要与已解释术语**：摘要=背景不是指令；冲突以当前原话为准；已解释的词不重复解释；
   定义缺失要补一句，不装作记得完整定义。
7. **输出契约**：默认只写「结论 / 依据 / 建议」三块，≤250 字；解释一步 ≤450 字；
   用户说「详细」≤800 字；发送前数一遍字数。
8. **工具与敏感信息**：最多 1 次只读工具，查不到就停；配置文件/密钥打码。

| 命令原文问题 | 1,265 字 | 1,159 字 | **415 字** |

结论：提示词在 `deepseek-official/deepseek-flash` 上达到设计目标；在
`workbuddy/cn:deepseek-v4.1-flash` 上仍超 3-4 倍——该模型不遵守字数预算。
要全模型一致，下一步需要在宿主侧加长度闸（或默认用 deepseek-flash）。

### 术语台账（与压缩提示词打通）

- **正文**：任何技术词、缩写、产品内部概念第一次出现时解释；同一段最多 2 个；
  已解释过的不重复；只有用户明确再问才展开。
- **压缩**：第七段「已解释术语」保存「术语：一句极简定义」，最多 10 条、每条 ≤30 字；
  再压缩时并进新台账，已经解释过的词不能丢。
- **实测**：一次压缩从 10 轮对话里抽出 7 条术语（构建 / 提交 / md5 / p50 / 长任务 / import / profile），
  定义都在 30 字内；再压缩后 19/19 锚点仍在。
- **标签统一**：摘要注入用「【本次对话此前的整理摘要（含「已解释术语」）】」，
  正文提示词引用同一个名字，模型不会对不上号。

### 没做的 / 需要知道的

- 老摘要没有第七段：下一次 `/compact` 会补上；在补上之前，正文按「摘要里没有台账」处理，不影响使用。
- 长度预算在 workbuddy 上不生效；这是模型差异，不是提示词措辞能完全解决的。
- 871 条测试全过（新增 11 条对话提示词契约测试；压缩契约从六段改七段，相关夹具同步）。

## 流式跟随：跟到写完为止，停下只由用户决定（2026-11-07）

> 用户原话：「小助手插件的内容生成时的自动跟随有点问题，不知道是bug还是设计的
> 不符合使用直觉，请排查并修复」。

### 一、先量了什么

「自动跟随」可能指三种东西，逐条分开了：

| 候选 | 是不是问题 | 依据 |
| --- | --- | --- |
| ① 滚动跟随（生成时把画面跟到新内容） | **是**，本次修的就是它 | 真机采样，见下 |
| ② 定位跟随（浮窗/气泡跟着选中的正文跑） | 不是 | 浮窗是 `position:fixed`，生成期间没有任何定位写入 |
| ③ 视觉跟随（高亮框/焦点环跟着内容变） | 不是 | 生成期间只有正文重画，高亮层在选中结束时已经释放 |

### 二、真机上的实际表现（3081，1920×827，非无头环境不可见的差异都不算）

正文区实测 **348px 高**（浮窗 548×519）。在这个高度上，「一屏」只有约五行字。
而小助手的真实回答是 **1335～2916 字**（`$DSH_HOME/explain-assistant/sessions`
里 11-07 那 12 条记录的长度，中位数 1464 字）——**三到八屏**。

旧行为（0.3.0 及以前）用一次真机采样写成时间线：

| 时刻 | 发生了什么 |
| --- | --- |
| 提问后 | 问句气泡停在可视区**下沿之外 106px**，模型思考的 **19 秒**里一直看不见自己问的那句 |
| 开始吐字 +2s | 画面跟着走，问句升到顶端 |
| 问句贴住顶端 | **跟随永久停止**（旧规则：问句到顶就停） |
| 之后 15 秒 | 正文从 2948px 长到 3378px，画面一动不动 —— 新内容全在看不见的下方 |
| 滚回底部 | **也不跟**：下一帧同一条几何规则又把「暂停」置上，用户没有任何办法恢复 |
| 生成结束 | `scrollTop` 2822 → 1777（内容从 3378px 掉到 2353px：窗口裁掉最上面一轮 −311px、上一轮从展开退回折叠 −612px） |

所以这条不是"设计得激进"，而是**三个缺陷叠在一起**：停得太早、停了恢复不了、停下时没有任何提示。

### 三、根因（四条，都能指到代码）

1. **一条会永久锁死的几何规则**：`followStreaming` 里「问句顶到正文区顶端 → `followPaused = true`」。
   它的本意是 2026-10-31 那句「避免模型输出太快导致用户读不完」，但正文区只有 348px，
   等于**一屏之后就不跟了**；而且它是每帧重算的，用户滚回底部也会在下一帧被重新置上。
2. **容差太大**：`FOLLOW_NEAR_BOTTOM = 120px`（约六行）。用户往上滚五六行想读清楚，
   位置仍算"接近底部"，下一块内容一到就把他拽回底部 —— 想停停不下来。
3. **连接阶段的上滚不算"接管"**：滚动监听里的判据是 `isBusy && state.text`，
   而模型思考那十几秒里 `text` 还是空的。用户正是趁那段时间往上翻，第一个分片一到就被拽走
   （真机实测：上滚 400px 停在原地 1.8 秒，内容一开始长，画面立刻被拉回）。
4. **问句没有当场带进视野**：注释写着"换了一问先把这一问带进视野"，代码里其实没有这一步。

### 四、修法

| 改了什么 | 现在怎么判 |
| --- | --- |
| 删掉「问句顶到顶端就停」 | 要不要停**只由用户自己的滚动决定** |
| 容差 120px → **48px**（三行） | 往上翻五六行就算接管，不再被拽回去 |
| 滚动监听判据 `isBusy && text` → `isBusy` | 连接阶段的上滚同样算接管 |
| 新的一问：当场 `scrollTop = scrollHeight` | 问句立刻进视野，不用等第一个分片 |
| 暂停时右下角出现「**回到最新**」（sticky，负 margin） | 点击或滚回底部都恢复跟随 |
| 新增「阅读位置锚点」：记活体块 + 历史里还看得见的头两轮 | 落地上方内容变短时按位移补 `scrollTop`，正在读的那一段不被顶走 |

「回到最新」这颗按钮挂在滚动内容里，用 sticky + `margin-top:-44px` 抵掉自身高度
（不是为了省事：absolute 定位的后代会被算进 `scrollHeight`，正是 warm-ui 上一轮
"能滚到空白"的根因）。

### 五、真机实测（同一台 3081、同一会话、CDP 驱动真事件）

| 判据 | 修前 | 修后 |
| --- | --- | --- |
| 提问后问句是否可见 | 下沿外 106px，19 秒看不见 | 正文区 348px 内、`top=261`，立刻可见 |
| 1000+ 字回答是否跟到底 | 到约一屏（≈2822px）就停 | 全程跟随：正文 3987px，`scrollTop` 3619（差值 19～38px 的缓动余量） |
| 真滚轮上滚 2 格 | 1.8 秒后被拽回底部 | 停在 1693px；5 秒后内容长到 2485px 仍停在 1693px |
| 暂停提示 | 无 | `回到最新` 按钮出现（`hidden=false`） |
| 点「回到最新」 | 无此入口 | 立刻贴底（`scrollTop = max`），按钮收起 |
| 滚轮滚回底部 | 不恢复 | 自动恢复跟随（`gap` 26px 并继续收敛） |
| 生成结束 | 2822 → 1777（被顶走 1045px） | `scrollTop == max`（贴底者仍贴底，不额外跳） |

### 六、没做的 / 需要知道的

* 这次**推翻**了 2026-10-31 那条「问句到顶就停」。理由是它与 348px 的正文区、1300～2900 字的
  回答长度不兼容，且不可恢复。如果你仍想要"别跟太快"，正确的做法是给一个跟随开关，
  而不是用几何位置去猜用户的阅读速度 —— 本次没有加开关。
* 「上一轮落地时从展开退回折叠（−612px）」是既有设计（最新一轮永远完整展开），
  这次只是让阅读位置不再因此跳走，没有改折叠策略本身。
* 采样来自单机（Chrome / Windows / AMD 集显），不代表低端机与 4K 屏。

## 已知限制（如实写）

1. **归档墓碑是内存态**：插件重启后丢失。若重启后仍有"晚到的写入"，理论上可能把已清理的文件重建出来；
   兜底是下一次归档检查。
2. **修复前落库的老记录补不出依据**：早期版本落库时没写 `evidence` / `tools` / `images`，
   这些老记录展开后仍然是空的，**无法追溯补齐**。
3. **占用百分比是启发式估算**：小助手不是 DSH 会话，没有可精确测量的 Session，
   所以按固定文本密度估算并**始终标注「估算」**；拿不到模型容量时显示「占用未知」，不编造数字。
4. **依据分级第三级较难出现**：「无从得知」需要一条"未完成 / 不可读"的卡片，
   在正常数据下不易构造，因此这一级主要是防御性设计。
5. **"切换主对话不串记录"只在接口层验证过**：页面上的点击级验证尚未做。
